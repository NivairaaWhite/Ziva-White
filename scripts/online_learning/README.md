# ZivaWhite Online Learning Management Kit

## Scope

This is the tooling to *manage* online (continual) learning --
safely updating the model from a live stream of new data without it
silently degrading or forgetting what it already knew.

"Online learning" here means the machine-learning sense: incremental model
updates from streaming data, as opposed to one-off batch training.

**No data ships with this kit.** The files below are yours: your feedback log, your held-out eval
set, and a rehearsal sample drawn from the conversations in your datasets folder.

## The five pieces, and why each exists

| File | Role | Why an online learning system needs it |
|---|---|---|
| `feedback_log.jsonl` | Raw signal stream (yours) | Every model interaction plus the user's real reaction (accept/edit/reject/implicit) — this is the actual fuel for learning. Without it you're just guessing what "good" looks like. |
| `replay_buffer_sample.jsonl` | Rehearsal set | Sampled by `build_replay_buffer.py` from YOUR conversations in the datasets folder. Mixed into every update so the model doesn't catastrophically forget old behavior while learning new patterns — the single most common failure mode in online learning. |
| `eval_benchmark.jsonl` | Fixed yardstick (yours) | Held out, never trained on. Re-run after every update to catch regressions before they ship. If this set isn't fixed, you lose your ability to tell "improved" from "just different." |
| `drift_monitor_log.jsonl` | Distribution watchdog | Generated by the loop script. Flags when incoming data starts looking meaningfully different from what the model was originally trained on — a leading indicator that quality issues are coming even before eval scores drop. |
| `version_registry.jsonl` | Decision audit trail | Generated by the loop script. Every update attempt logged with what went into it and whether it was promoted — so a bad update can be traced and rolled back. |

## What's real data vs. a stub — read this before trusting any number

- **Real, computed from actual data:** batch acceptance/edit/reject rates,
  category distribution, average input length, the drift score.
- **Now wired to a real model** (previously a stub): `run_eval_suite()` in
  `online_learning_loop.py` loads an actual checkpoint through
  `zivawhite.router.ZivaWhite` and generates a real response for
  every `eval_benchmark.jsonl` record when you pass `--checkpoint`:

  ```bash
  python3 online_learning_loop.py --checkpoint ../../../runs/ziva/checkpoint.pt
  ```

  Scoring is a free, dependency-free lexical-overlap heuristic (token-F1
  against `reference_output` + an `acceptance_criteria` keyword check), so
  it works fully offline. It is a crude signal: good for "did this
  checkpoint get worse", not for ranking answers. (The old `--judge llm`
  option was removed: it depended on API connectors this project no longer
  has.)
- Run with **no** `--checkpoint` and this still behaves exactly like the
  original stub: `run_eval_suite()` returns `None`, and every
  `version_registry.jsonl` entry says `"decision_basis":
  "heuristic_pending_real_eval"` for exactly the reason described below.
- Even wired up, this is honest about being a *small-model* signal: a
  freshly-bootstrapped or lightly-trained checkpoint will score low
  because its output is genuinely still rough, not because the eval is
  broken — see "A small model trained on a little data" in `../../datasets/README.md`.

## Where your files go

Inputs are looked for in `<datasets folder>/_eval/` first (the folder name starts with `_`, so
training never reads it), then in this kit's `data/` folder. Outputs (`replay_buffer_sample.jsonl`,
`drift_monitor_log.jsonl`, `version_registry.jsonl`) are written to `data/`.

Formats, one JSON object per line:

```jsonc
// feedback_log.jsonl
{"interaction_id": "i1", "timestamp": "2026-10-06T10:00:00Z", "category": "support", "input": "...",
 "model_output": "...", "feedback_type": "accept",   // accept | reject | edit | implicit_positive | implicit_negative
 "corrected_output": "..."}                          // required (non-empty) when feedback_type is "edit"

// eval_benchmark.jsonl
{"eval_id": "e1", "category": "support", "input": "...", "reference_output": "...",
 "acceptance_criteria": ["mentions refunds"]}
```

## Run order

```bash
cd scripts
python3 build_replay_buffer.py        # -> data/replay_buffer_sample.jsonl  (from YOUR datasets/ conversations)
python3 online_learning_loop.py       # -> data/drift_monitor_log.jsonl, data/version_registry.jsonl
                                       #    (add --checkpoint ../../../runs/ziva/checkpoint.pt
                                       #    for a real eval_score instead of null)
python3 validate_dataset.py           # sanity-checks every file that is present
```

## Wiring this into ZivaWhite for real

1. `run_eval_suite()` already calls your model; if the lexical heuristic feels too coarse once you
   have a stronger checkpoint, a better judge would have to be a model you run locally.
2. Point your real interaction stream at `feedback_log.jsonl` (accept = used as-is, edit =
   user-corrected, reject = discarded, implicit_positive/negative = inferred from what the user did next).
3. Tune `BATCH_SIZE`, `REHEARSAL_RATIO`, and `DRIFT_ALERT_THRESHOLD` at the top of
   `online_learning_loop.py` once you have real volume: the values are starting points, not tuned constants.
4. Route `promoted: true` versions into whatever actually deploys a new checkpoint in your stack
   (autolearn picks up new files in `datasets/` by itself); route `flag_for_review: true` drift entries to
   a human before the next batch trains on top of them.
