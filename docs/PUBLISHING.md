# Publishing a ZivaWhite model

Four destinations, one export. Everything below starts from the folder `export` writes:

```bash
# the tokenizer is found in runs/chat/tokenizer/ by itself
python -m zivawhite.app export --checkpoint runs/chat/checkpoint.pt \
       --out exports/my-model --name My-Model --license apache-2.0 --data_note @data/chat/smol.jsonl.provenance.json --verify
```

`exports/my-model/` then holds `model.safetensors`, `config.json`, `generation_config.json`, `tokenizer.json`,
`tokenizer_config.json` (with the chat template), `special_tokens_map.json`, a generated `README.md` model card, and an
Ollama `Modelfile`. It is a plain `LlamaForCausalLM`, so nothing needs custom code. `--verify` reloads it with
`transformers` and compares logits with your checkpoint (it refuses to finish if they differ). **Publish this folder,
and only this folder.** A training run folder holds optimizer state and pickle checkpoints (a security risk to
distribute) and no `config.json`, so it is not a loadable model.

## Before you publish anything

- [ ] **Training data license and provenance.** `data` writes a `*.provenance.json` for every dataset it prepares.
  Hand them to `--data_note`. A dataset's own license is not the only constraint: several popular sets were
  *generated by commercial LLMs* (SmolTalk is tagged "Synthetic"; OpenHermes-2.5 is largely GPT-4 output;
  UltraFeedback's completions come from a mix of open and proprietary models; `open-phi/textbooks` records GPT-3.5 as
  its generator and its card states **no license at all**). The providers' terms of use may restrict using outputs to
  train other models. Read them. This is the single most likely thing to bite a published model.
- [ ] **Imported weights.** If you started from an open model (`import-hf`), its license governs your derivative
  (Apache-2.0 for SmolLM2; the Llama Community License has its own conditions).
- [ ] **Your license** must be compatible with both of the above. The card leaves `license:` unset until you pass `--license`.
- [ ] **Read the card.** Fill in the TODO under *Training data*. The generated limitations section is deliberately
  blunt: small models are often wrong, and nothing here aligns a model for safety.
- [ ] **No personal data** in anything you trained on.

(This is a checklist, not legal advice.)

## Hugging Face Hub

```bash
pip install -r requirements-publish.txt
export HF_TOKEN=hf_...                                  # a write token from huggingface.co/settings/tokens
python -m zivawhite.export_hf --checkpoint runs/chat/checkpoint.pt --out exports/my-model --push you/My-Model          # private
# look at it on the site; when you are happy, make it public in the repo settings, or re-run with --public
```

Then anyone can use it:

```python
from transformers import AutoModelForCausalLM, AutoTokenizer
tok = AutoTokenizer.from_pretrained("you/My-Model")
model = AutoModelForCausalLM.from_pretrained("you/My-Model")
ids = tok.apply_chat_template([{"role": "user", "content": "Hello!"}], add_generation_prompt=True, return_tensors="pt")
print(tok.decode(model.generate(ids, max_new_tokens=100)[0][ids.shape[1]:], skip_special_tokens=True))
```

Notes: the repo is created private by default; `model.safetensors` is written with the `format: pt` metadata that
`transformers` requires; bf16/fp16/fp32 are chosen with `--dtype`.

## Ollama

Verified against Ollama's current import documentation: it can import a **safetensors directory** for supported
architectures, which include Llama, or a **GGUF** file.

```bash
cd exports/my-model
ollama create my-model -f Modelfile        # Modelfile says FROM . (this folder)
ollama run my-model
```

The generated `Modelfile` reproduces the chat format (`<|role|>` turns) and stops on every role tag. I wrote it from
Ollama's documented syntax and **have not run it against Ollama**: after `ollama run`, ask the same question through
`python -m zivawhite.app ask` and compare. If replies differ, the `TEMPLATE` is the first suspect.

**GGUF route** (for quantization, or if the direct import complains):

```bash
git clone https://github.com/ggml-org/llama.cpp && cd llama.cpp
python convert_hf_to_gguf.py ../exports/my-model --outfile my-model.f16.gguf --outtype f16
# optional 4-bit: ./llama-quantize my-model.f16.gguf my-model.q4_k_m.gguf Q4_K_M
# then change the Modelfile's first line to: FROM ./my-model.q4_k_m.gguf
```

**The snag for a tokenizer you trained yourself:** llama.cpp identifies a BPE tokenizer by hashing how it tokenizes a
test string, so an unfamiliar one stops with `BPE pre-tokenizer was not recognized` and prints a hash. Your tokenizer
uses the plain GPT-2 byte-level regex, so the documented fix is to map that printed hash to `"gpt-2"` in
`get_vocab_base_pre()` in `convert_hf_to_gguf.py`, then re-run. I confirmed the mechanism in llama.cpp's own
documentation and issue threads but could not run it here. A model imported with `import-hf` carries its original,
already-recognised tokenizer and avoids this.

Because it is a standard Llama checkpoint, `vllm serve exports/my-model` (or TGI, SGLang) should work and is the right

## Serving it yourself (no export needed)

`python -m zivawhite.app serve` exposes `/v1/chat/completions` and `/v1/models` in the OpenAI wire format, with
`"stream": true` for server-sent events, so existing OpenAI clients work by changing the base URL:

```python
from openai import OpenAI
client = OpenAI(base_url="http://localhost:8000/v1", api_key="anything-or-your-ZIVAWHITE_SERVER_API_KEY")
for chunk in client.chat.completions.create(model="ziva-white", stream=True, messages=[{"role": "user", "content": "hi"}]):
    print(chunk.choices[0].delta.content or "", end="")
```

It only generates text; like every route except `/v1/assistant`, it can never touch your device.

## AIKosh (IndiaAI Mission)

What I could verify on AIKosh's own pages and the IndiaAI announcement (the portal is `aikosh.indiaai.gov.in`; the
name is also written "AIKosha"):

- The platform has **Explorer, Contributor and Organization-admin roles. Only Contributors can upload models, and an
  upload is subject to verification** by the organization admin and the platform admin.
- Contributing is **organization-based**: a designated person registers as an Explorer, then starts onboarding the
  organization, submits documents, accepts the terms, and waits for approval. The dataset call for contributions says
  only institutional entities may contribute datasets. So an individual hobbyist cannot necessarily upload directly;
  you may need an institution (a company, university, or registered body) behind it.
- Read their User Manual and FAQ first: `https://aikosh.indiaai.gov.in/home/user-manual/` and
  `https://aikosh.indiaai.gov.in/home/faqs/`.

What I could **not** verify, and so did not build on: that AIKosh requires or favours any particular sector
(agriculture, education, ...); the dataset name `coild-aikosh` from your notes; and the claim that listing a model there
"establishes prior art" in Indian IP law. Ask AIKosh, or a lawyer, rather than rely on those. Since your direction is a
general-purpose model, nothing I found says it has to be domain-focused, and the exported folder + model card
(with honest data provenance) is what any such review would want to see.
